## 現在の状態

メッセージの投入・取り出しが動く最小実装、使用例のテスト、演習を含む第 1 レッスンを用意した段階。学習者の回答はまだ確認しておらず、学習課題は未完了。作業管理には GitHub Issues を使う。

## レッスンを開く

WSL のターミナルで、リポジトリのルートから実行する。

```sh
./learn
```

第 1 レッスンを Windows 側の既定の HTML アプリで開く。HTML の関連付けはブラウザにしておく。Windows 連携が有効な WSL を使い、サーバー起動・Rust のビルド・追加ツールの導入は不要。演習コードがコンパイルできない状態でも教材を開ける。

## コードを動かす

Rust 2024 Edition に対応する Rust と Cargo を使う。外部クレートへの依存はなく、リポジトリのルートで次を実行できる。

```sh
cargo test --offline
```

これはライブラリなので、`cargo run` ではなくテストから動作を確かめる。使用例だけを実行するときは `cargo test --offline --test broker` を使う。

## 出発点の仕様

- `Broker::new()`：空のブローカーを作る。
- `publish(String)`：本文の所有権を受け取り、キューの末尾に入れる。
- `receive() -> Option<String>`：先に投入した本文から一件ずつ取り出す。空なら `None` を返す。

受信済みの本文はキューに残らない。空になった後も再び投入して受信できる。メッセージの ID、宛先、処理完了の管理はまだ持たない。

読む順序と着目点は、[レッスン 1](lessons/0001-message-ownership.html#trace)で案内する。

## 学習の順序

既存製品を再現するのではなく、学習用の独自仕様で進める。

1. 単一キュー：投入したメッセージを順に取り出す。所有権の移動と、参照を返す場合の違いを学ぶ。
2. 処理中の管理：受信と処理完了を分ける。ACK で完了、NACK でキューに戻す仕組みを通して、状態とデータの持ち方を考える。
3. 複数キュー：宛先キーに応じて一つのキューを選ぶ。エラー処理とコレクション操作を整理する。
4. 抽象化：本文をジェネリクスで扱う。宛先の完全一致・接頭辞一致という二つの選択方針を具体的に実装してから、共通部分を trait にする。

各段階の細かな仕様は、取りかかる前にレッスン内の演習で確定する。次の段階は、前の段階で動いていたコードへの仕様変更として進める。

## 学習の進め方

[レッスン 1：本文の所有者を追う](lessons/0001-message-ownership.html) をブラウザで開いて始める。レッスンを学習の入口とし、目標・解説・コードリーディング・演習・振り返りを一つのページで進める。

| 場所 | 役割 |
| --- | --- |
| `lessons/` | 解説、問い、演習の仕様と完了条件 |
| `src/`・`tests/` | 手元のエディタで読み、変更し、テストするコード |
| `reference/` | 後から引く要点集 |

回答・質問・レビュー依頼は AI との会話で行う。レッスンから回答が自動送信されることはない。

一緒に学習を進めるときは、このリポジトリを作業ディレクトリにして `/teach 続きから進めたい` と伝える。AI は学習目的・記録・現在のコードを確認し、今のレッスンの続きから支援する。毎回新しいレッスンを作るわけではなく、途中の質問やレビュー依頼には `/teach` を付け直さなくてよい。`./learn` は教材を開く入口、`/teach` は対話で学習を進める入口として使い分ける。

出発点は未実装の穴を埋める雛形ではなく、小さくても動く Rust ライブラリ。最初の演習では `peek` を追加するが、その解答や ACK・振り分けなどの後続機能は、出発点の実装に含めない。

実装とテストの後は、自分の判断を説明してレビューを受け、同じ仕様を満たす参考実装と比較する。比較で得た理由に基づいて必要な改善を行い、完了した段階をコミットで残す。

参考実装は唯一の正解ではない。動作が合うだけでなく、[到達の目安](MISSION.md#到達の目安)に沿って判断を説明できることを大切にする。
