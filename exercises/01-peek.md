# 課題 1：取り出さずに先頭を読む

## 今回の仕様変更

ブローカーを使う側から「次に届く本文を確認したいが、まだ受信はしたくない」という要望が来た。

既存の `receive` は、先頭の本文をキューから取り出し、所有権を受信側へ渡す。この動作は変えずに、本文を読むだけの `peek` 操作を `Broker` に追加する。

## まず動かして読む

リポジトリのルートで実行する。

```sh
cargo test --offline --test broker
```

次の順で読む。今は全機能を覚える必要はない。

1. [tests/broker.rs](../tests/broker.rs)：利用者として投入と受信の流れを追う。`first` を作った直後、`publish` の後、`received` を受け取った後で、本文の所有者が誰かを考える。
2. [src/lib.rs](../src/lib.rs)：`Broker` が保持するもの、`publish` と `receive` がその状態をどう変えるかを追う。`String` と `Option<String>`、`&mut self` に注目する。
3. 同じファイルの `new` と `#[derive(Default)]`：空のブローカーの初期化を確認する。今は独自の trait 設計に進まず、空の状態を作る仕組みとして読む。

## 追加する動作

- メッセージがあれば、先頭の本文を読み取り専用の参照として返す。本文の所有権はブローカーに残る。
- 空なら、値がないことを `Option` で表す。空であることを理由にパニックさせない。
- `peek` 自体は、キューの内容と順序を変えない。
- 呼び出し元は、読み取るためだけにブローカーを可変で借用する必要がない。
- `publish` と `receive` の既存の動作は維持する。

メソッドの型と実装、追加するテストは自分で考える。今回は ACK、複数キュー、ジェネリクスを追加しない。

## テストで確かめる場面

公開操作だけを使って、少なくとも次を確かめる。

1. 空のブローカーの先頭を読んでも値がない。
2. 異なる本文を二つ投入すると、先に投入した本文が読める。
3. 続けて二度読んでも同じ本文で、まだ取り出されていない。
4. 読み取りを終えてから受信すると、先頭の本文を受け取れる。その後に読むと二件目が見える。
5. 最後の本文まで受信した後は、先頭を読んでも値がない。

確認には `cargo test --offline` を使う。内部のフィールドを公開してテストする必要はない。

## 完了の目安

- 上の場面を自分のテストで確かめ、既存テストも通っている。
- 戻り値と `self` の型を選んだ理由を説明できる。
- `receive` と `peek` で、本文の所有者がどう違うか説明できる。
- 本文の参照を後で使う予定がある間に `receive` を呼ぶと、何が問題になるか説明できる。必要なら手元で試し、コンパイラの指摘を読む。
