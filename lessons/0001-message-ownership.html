読むための最小限の知識

String を値として関数へ渡すと、所有権が移る。戻り値でも所有権を移せる。一方、参照を渡す場合は、所有者を残したままアクセスする。

原典：Rust Book：関数と所有権、参照と借用。

1. 一件の本文を追う

まずリポジトリのルートで、使用例のテストを動かそう。

cargo test --offline --test broker

使用例のテスト、実装の順に読む。本文を保持する場所と、publish・receive による状態の変化を追おう。new と #[derive(Default)] は、今は空の状態を作る仕組みとして確認すればよい。

使用例から、一件の流れだけを抜き出した。A・B・C の直後の所有者を考えよう。

let mut broker = Broker::new();
let first = String::from("注文を受け付けた"); // A
broker.publish(first);                     // B
let received = broker.receive()
    .expect("最初のメッセージがある");       // C

expect は値があれば中身を取り出す。ここでは先に一件投入しているので、その本文を受け取れる。公式仕様

2. コンパイル前に予想する

  1. A・B・C それぞれの直後、本文を所有しているのはどこ？
  2. B と C の間に println!("{first}"); を入れたら、コンパイルできる？ 理由は？
  3. publish の後も broker を使えるのはなぜ？ first と扱いが違う箇所を型から探そう。

まず自分の言葉で、この会話に回答してね。分からない箇所は「ここが分からない」で大丈夫。回答を見て、必要なところだけ一緒に確かめる。

自分で答えたあとに、考え方を確認する

A では first が所有する。B の呼び出しが終わると、本文は broker 内のキューに移っている。C ではキューから取り出した本文を received が所有する。

B の後に first を使うとコンパイルできない。publish の引数 message: String へ値を渡しているから。一方、ブローカーは &mut self として借りており、呼び出し元が所有したままなので、呼び出し後も使える。

receive が返した Option<String> から expect で本文を取り出し、received に移している。「元の変数名に戻る」わけではない。

3. 演習：取り出さずに先頭を読む

ここまでの説明ができたら、次は実装しよう。「次に届く本文を確認したいが、まだ受信はしたくない」という要望に応え、Broker に peek を追加する。

receive は本文を取り出して所有権を渡す。一方、今回の読み取りでは所有権をブローカーに残す。必要なら Rust Book：参照と借用を読み、所有権を渡さないアクセスと、借用中の変更の制約を確認しよう。

追加する動作

  • メッセージがあれば、先頭の本文を読み取り専用の参照として返す。本文の所有権はブローカーに残る。
  • 空なら、値がないことを Option で表す。空であることを理由にパニックさせない。
  • peek 自体は、キューの内容と順序を変えない。
  • 呼び出し元は、読み取るためだけにブローカーを可変で借用する必要がない。
  • publish と receive の既存の動作は維持する。

src/lib.rs にメソッドを、tests/broker.rs にテストを追加する。メソッドの型と実装は自分で考えよう。今回は ACK、複数キュー、ジェネリクスは追加しない。

テストで確かめる場面

公開操作だけを使って、少なくとも次を確かめよう。内部のフィールドを公開する必要はない。

  1. 空のブローカーの先頭を読んでも値がない。
  2. 異なる本文を二つ投入すると、先に投入した本文が読める。
  3. 続けて二度読んでも同じ本文で、まだ取り出されていない。
  4. 読み取りを終えてから受信すると、先頭の本文を受け取れる。その後に読むと二件目が見える。
  5. 最後の本文まで受信した後は、先頭を読んでも値がない。

変更したら、既存の動作も含めてテストする。

cargo test --offline

迷ったら、どの動作や型で困っているかをこの会話で教えてね。コンパイラのエラーなら、試したコードと自分が考えた原因を添えると、必要なヒントから一緒に考えられる。

4. 振り返りと完了の目安

上の場面を自分のテストで確かめ、既存テストも通ったら、次を自分の言葉で説明しよう。

  • 戻り値と self の型を選んだ理由。
  • receive と peek で、本文の所有者がどう違うか。
  • 本文の参照を後で使う予定がある間に receive を呼ぶと、何が問題になるか。必要なら手元で試し、コンパイラの指摘を読む。

レビューを頼むときは、変更したファイル、テスト結果、上の説明を教えてね。説明したあとに参考実装と比較する。このページには実装の解答を載せていない。
